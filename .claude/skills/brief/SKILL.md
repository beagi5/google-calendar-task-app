# ブリーフを書く

委譲の質はブリーフの質で決まる。実行役が強くても、ブリーフが弱ければ往復が増えて
総コストが上がる。このスキルはブリーフを**ファイルとして**残し、Claude の sidekick にも
外部モデルにも同じものを渡せるようにする。

## 手順

### 1. 委譲可能か判定する

以下に1つでも当てはまるなら**委譲しない**。lead が自分でやる。

- 成功基準が書けない（＝仕様がまだ固まっていない）
- どのファイルを触るかが列挙できない
- 途中で仕様が変わる見込みがある
- 対話的なデバッグや原因切り分けが必要

書けないことが分かったら、そう言って止める。無理にブリーフを作らない。
**ブリーフが書けないという発見自体が、このスキルの重要な出力。**

### 2. 計画のための探索は lead が自分でやる

ブリーフを書くのに必要な読み込みは委譲しない。どのファイルが効くかの見極めは
計画そのものを形づくるので、ここを他人に任せると計画が歪む。

### 3. ブリーフを書く

`.claude/briefs/<YYYYMMDD>-<slug>.md` に `template.md` の形式で書く。

書き方の原則:

- **成功基準はコマンドで確かめられる形にする。** 「正しく動く」ではなく
  「`npm run build` が通り、`grep -n 'accessToken' server/index.js` の結果が
  refreshAccessToken 経由のみになる」のように書く。
- **制約は「変えてはいけないもの」を書く。** やることより、やってはいけないことの方が
  漏れやすく、事故になる。
- **実装手順は書かない。** 手順を書き下すのは micromanage。何を満たすかだけ決める。
- **対象ファイルを列挙する。** ここに無いファイルは sidekick が触らない契約になる。

### 4. 委譲する

Agent ツールで `subagent_type: "sidekick"` を呼び、prompt にブリーフのパスと本文を渡す。
会話の経緯は渡さない。

### 5. 受け取る

sidekick の報告は「変更ファイル・基準の確認・PUSHBACK・やらなかったこと」で返る。
**中間の探索経過は読まない。** 基準と差分だけで判定する。

PUSHBACK が返ってきたら、それは失敗ではない。ブリーフの前提が間違っていた可能性が高いので、
実装を進めさせる前にブリーフを直す。

### 6. 検証する（任意）

独立性を上げたいときは:

- Claude 内で完結: Agent ツールで `subagent_type: "verifier"` に、ブリーフと差分だけ渡す
- 外部モデルに出す: `bash scripts/handoff.sh <ブリーフのパス>` で仕様＋差分を
  1つのテキストに書き出し、Gemini Pro 等に貼って違反だけ列挙させる

## テンプレート

`.claude/skills/brief/template.md` を使う。
