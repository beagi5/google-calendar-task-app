# 委譲構造の設計メモ

Cognition の Fusion（2026-09-11）と Sakana の Fugu Ultra v2（同）を読んで、
この環境で再現できる形に落としたもの。作業ルール本体は `CLAUDE.md`。

## 元になった知見

Fusion は lead（frontier、計画とレビュー）と sidekick（低コスト、実行）を
**並列に走らせ、それぞれ独立した永続文脈を持たせる**構成。会話全体を渡さず、
brief / result / feedback だけを交換する。主要コーディングベンチで最大39%効率化。

この構成から取った設計判断は4つ。

### 1. 安いトークンではなく、安いタスクで考える

Fusion の報告で最も重要な数字: lead を Opus 4.8 から Fable 5.1 に替えたところ、
トークン単価は2倍なのに**セッション総額は9%下がり、スコアは上がった**。
理由は「Fable は早く委譲して良いブリーフを書き、Opus は micromanage して
sidekick の仕事をやり直していた」。

→ 委譲の目的を「消費を減らすこと」に置かない。**往復を減らすこと**に置く。
  手順を細かく書き下すブリーフは、安く見えて高い。

同じことが実行役側にも言える。SWE-2（$0.75/Mtok）は GPT-5.6 Luna（$0.20/Mtok）より
275%高いのに、総コストは2%安くスコアは上。強い実行役は試行回数が少なく、
レビュー往復も減るため。**弱い実行役を選ぶのは節約にならない。**

### 2. 委譲の可否は「仕様で切れるか」で決める

Fusion の記事は「大半のコーディングタスクは明確なフェーズに分解できる」と書いているが、
同じ記事のベンチ表がその限界を示している。

| ベンチ | 単独 lead | Fusion | 差 |
|---|---|---|---|
| Vals Code Migration (Fable) | 54.6 | **57.3** | +2.7 |
| SWE-Atlas QnA (Fable) | 64.8 | **65.9** | +1.1 |
| DeepSWE 1.1 (Fable) | 64.3 | 63.1 | −1.2 |
| **Terminal-Bench 4 (Astra)** | 55.6 | **50.0** | **−5.6** |

劣化が集中しているのは Terminal-Bench。仕様がフェーズに切れるタスク（移行・QnA）では
委譲が性能を**上げる**が、状態が連続して途中で文脈を切れないタスク（端末操作・
対話的デバッグ）では構造そのものが税になる。

→ 判断基準は「安くしたいか」ではなく「このタスクは仕様で切れるか」。

### 3. 計画のための探索は委譲しない

Fusion がチューニング項目として挙げた3つのうち最も効くもの。
「計画に必要な探索は弱い sidekick に委譲してはならない。lead の計画そのものを
形づくるため。弱い sidekick は何が重要な情報かを判断できない」。

→ ブリーフを書くための読み込みは lead が自分でやる。
  委譲できるのは**仕様が確定した後の実装**だけ。

### 4. 検証者は実装者の思考過程を見ない

Fusion では lead がレビューを持つ（第三者ではない）。ただし lead は sidekick の
**中間ツール結果を見ない**。自分が書いた成功基準と、出てきた成果物だけを見る。
実装者の合理化の痕跡を遮断する設計。

→ このリポジトリでは3段階の独立性を用意した。下にいくほど独立性が高い。

1. lead が成功基準と差分だけ見る（最低限。常にやる）
2. `verifier` サブエージェント（コールドスタートなので実装の経緯を物理的に知らない）
3. 外部モデル（`scripts/handoff.sh`）

## 構成要素

| ファイル | 役割 |
|---|---|
| `CLAUDE.md` | 作業プロトコル本体。全セッションに自動で効く |
| `.claude/agents/sidekick.md` | 実行役（Sonnet 5）。ブリーフのみを契約面とする |
| `.claude/agents/verifier.md` | 独立検証役（Sonnet 5）。読み取り専用、修正権限なし |
| `.claude/skills/brief/` | ブリーフ生成スキル＋テンプレート |
| `.claude/briefs/` | 書いたブリーフの置き場（履歴として残す） |
| `scripts/handoff.sh` | 外部モデルへの検証依頼パケット生成 |

サブエージェントは毎回コールドスタートする。これは制約ではなく、
**ブリーフを唯一の契約面にする**という Fusion の設計そのもの。

## 他社モデルの位置づけ

トークン消費の分散のために Gemini Pro / Perplexity / ChatGPT を使いたい場合、
**実行役には向かないが、検証役と調査役には向く**。役割は2枠に固定する:
検証役＝Gemini Pro、調査役＝Perplexity と ChatGPT 無料版（交換可能）。

| ツール | 役割 | 根拠 |
|---|---|---|
| Claude Code (Opus 5) | lead。計画・ブリーフ・レビュー | 意図の保持者は1人に固定する |
| Claude sidekick (Sonnet 5) | 実行 | ツールと永続文脈が必要な役はここにしか置けない |
| Gemini Pro | 独立検証、大量読み | **lead の推論を物理的に見られない**ため独立性が本物。長文脈で差分レビューに向く |
| Perplexity / ChatGPT 無料版 | 外部調査（**交換可能**） | コードループの外。リポジトリ接続が不要な唯一の領域 |

### 調査役は交換可能な1つの枠として扱う

Perplexity と ChatGPT 無料版は**同じ役割（外部調査）を持つ交換可能な1枠**とする。
どちらも無料枠で回数が限られるため、片方を使い切ったらもう片方に回す。
役割を分けて覚えるより、「調査はこの枠」と1つにまとめた方が運用が続く。

調査役に渡すもの:

- ライブラリ・APIの仕様確認（googleapis の挙動、OAuth のリフレッシュ仕様など）
- エラーメッセージの事例検索
- 設計の一般論（「この種の実装のよくある落とし穴」）

調査役に渡さないもの:

- **リポジトリのコードそのもの。** 接続がないので断片しか渡せず、断片への回答は
  文脈を欠いて誤りやすい。コードを見た判断が要る場面は Gemini Pro（検証役）か
  Claude 側に置く。
- 実装の指示。調査結果は lead が受け取ってブリーフに反映する形にする。

無料枠を検証役（差分レビュー）に使わないこと。差分は長く、無料枠ではすぐ尽きる上、
途中で切れた検証は「合格」と見分けがつかず最も危険な失敗の仕方をする。
**検証役は Gemini Pro に固定する。**

実行役を外部チャットに置かない理由:

- 実行役にはリポジトリへの接続・ツール・永続文脈が要る。チャット窓にはない
- コピペで繋ぐと、Fusion が削ったはずの往復コストが**人間の時間**に転嫁される
- 弱い実行役はレビュー往復を増やし、総コストを上げる（上記1の SWE-2 の結果）

外部モデルへの受け渡しは `scripts/handoff.sh` に一本化してある。
仕様と差分だけを出力し、会話履歴は含めない。

## まだやっていないこと

**検査面（`npm run verify`）が未整備。** 現状 ESLint 設定がなく、テストは CRA の雛形のみ、
server 側は皆無。成功基準を「コマンドで確かめられる形」で書くには、確かめる
コマンドが先に要る。ここが埋まるまで、成功基準の一部は目視判定になり、
Fusion の利得（レビュー往復の削減）は部分的にしか出ない。
