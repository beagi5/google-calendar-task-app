# ブリーフ: カレンダー認証クライアントの一元化とトークンリフレッシュの共通化

日付: 2026-09-15
実行役: sidekick (Sonnet 5)

## タスク

Google カレンダーAPIを呼ぶ全経路が、**トークンリフレッシュを含む単一のヘルパー**を
経由するようにする。現状、リフレッシュ処理があるのは7経路のうち1つだけで、
アクセストークンの期限切れ後は残り6経路が 401 で失敗する。

## 現状（lead が確認済み）

- `server/index.js:214` `/api/calendar/events` — クライアントを**インラインで組み立て**(221)、
  401時のリフレッシュ処理を持つ(251-270)。ただしリフレッシュ後に `events.list` の
  呼び出しを丸ごと**複製**している。
- `server/index.js:405` `getCalendarClientForRequest(req)` — 共有ヘルパー。
  **リフレッシュ処理を持たない。** 呼び出し元は 337, 393, 422, 448, 578, 610 の6箇所。
- リフレッシュ時に `req.session.userTokens.accessToken` のみ更新（refreshToken は据え置き）。

## 対象ファイル

- `server/index.js` — 上記の一元化

※ ここに無いファイルは変更しない。フロント側(`src/`)は対象外。

## 制約（変えてはいけないもの）

- **全APIエンドポイントのリクエスト/レスポンス形式を変えない。** パス、ステータスコード、
  JSONのキー名すべて。フロントは無変更で動き続けること。
- 認証失敗時のメッセージ `'Calendar access expired. Please re-authenticate.'` と
  ステータス 401 を維持する。
- 新しい依存パッケージを追加しない。
- `requireAuth` ミドルウェアの挙動を変えない。
- セッションに保存するトークンの構造 (`req.session.userTokens`) を変えない。

## 成功基準

- [ ] `grep -c "new google.auth.OAuth2" server/index.js` の結果が **1**
      （OAuth2クライアントの組み立てが1箇所に集約されている）
- [ ] `grep -c "refreshAccessToken" server/index.js` の結果が **1**
      （リフレッシュ処理が1箇所に集約されている）
- [ ] `node --check server/index.js` がエラーなく通る
- [ ] `npm run build` がエラーなく完了する
- [ ] `getCalendarClientForRequest` の既存6箇所の呼び出し
      (337, 393, 422, 448, 578, 610 付近) が、リフレッシュを経由する経路に乗っている
- [ ] `/api/calendar/events` のリフレッシュ後の `events.list` 呼び出しの重複が解消されている
      （同じクエリを2回書いている箇所が無い）

## 範囲外

- テストの追加（別タスク）
- ESLint 設定の追加（別タスク）
- refreshToken 自体の更新・永続化（DB が無いため別設計が必要）
- エラーメッセージの文言改善

## 反論してほしい点

- 「全経路を同じヘルパーに通す」と言っているが、`/api/calendar/events` だけ
  `events.list` のリトライが必要で、他は操作内容が違う。**リトライを汎用化する形
  （操作をコールバックで受ける等）が実装として妥当か**、それとも
  クライアント生成だけ共通化してリトライは各所に残す方が素直か。
  前者で破綻しそうなら、着手前に報告してほしい。
